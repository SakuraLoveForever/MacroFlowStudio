# MacroFlow Studio 渐进式优化：Agent 执行提示词

请基于当前工作区，对 MacroFlow Studio 进行渐进式“依赖减耦、列表性能优化、UI减法、启动与发布优化”。先核实事实，再实现；不要机械执行已完成的事项，也不要一次性重写。

## 一、执行边界

- 保留 Python、Tk、ttkbootstrap 和当前核心功能。
- 不引入 Electron、Qt、Web 前端、依赖注入框架、事件总线、插件框架或只有一个实现的接口/工厂。
- 优先使用现有依赖和标准库。删除旧兼容导入路径，不新增转发、别名或动态兼容入口。
- 每个阶段结束仍须保留完整可工作的产品。界面减法是调整入口和层级，不是删除业务能力。
- 开始前检查 git status 和现有 diff；当前工作区可能包含用户或其他 agent 的未提交修改，必须保留并在其基础上工作，不得重置、覆盖或混入自己的提交。
- 不启动应用界面，不运行可见界面测试，不操作、截图或目视检查窗口；不得以 Tk().withdraw()、透明窗口或后台启动 GUI 的方式绕过约束。
- 只运行不创建软件界面的单元测试、性能测试、编译检查、构建和静态产物校验。涉及 OCR 依赖裁剪时，可执行无界面、离线的真实图片识别回归。
- 正常技术取舍自行决定并连续推进；只有确实缺少关键决策、超出任务范围或涉及无法逆转的重大影响时才询问。

## 二、已发现的问题与应保留的现状

以下是交接时对当前源码的观察，你仍需核对工作区是否更新：

1. `ui/app/__init__.py`、`execution/player/__init__.py` 有大量兼容重导出，并在包入口组合 Mixin；`ui/dialogs/__init__.py` 也集中导入大量实现。不能只改调用方 import 路径，因为导入子模块仍会执行父包的 `__init__.py`。
2. `tests/common.py` 同时导入 MacroFlowApp、Tk、OpenCV、NumPy、识别和 Windows 输入模块，还用 `_PackagePatch` 扫描包及所有子模块进行 patch。多个测试文件很大。
3. 部分现有测试直接创建 `tk.Tk()` / `tk.Toplevel()`，随后隐藏或设置透明；因此必须先处理测试边界，不能一开始就盲目运行全量 discover。
4. 动作表和工作流表使用位置索引作 Treeview iid，编辑操作多次触发全量重建。动作列表只显示前 20,000 条；重建时会全量计算摘要和列宽。
5. `_checkpoint_action_edit` 每次深拷贝整个动作列表，最多保留 100 份快照。仅改 Treeview 更新不能消除这部分成本。
6. `_measure_text_width` 每次创建 Font；工作流表重建还会重建全局模块表。模块名称/启用状态查询经 `registered_module_object` 反复读取、解析模块配置。
7. 主窗口最小宽度常量为 1180，侧栏宽度为 372，正文字号为 9pt，小字号为 8pt，存在 `Playback speed` 英文标签。
8. PaddleOCR 引擎已经在 `_get_engine()` 中按需导入，且已外置到 `paddle_ocr`。但识别包装模块仍顶层导入 NumPy、OpenCV，主程序经多个入口提前加载相关依赖。
9. `AGENTS.md` 已区分开发检查点与交付检查点；`build.ps1` 已有输入哈希复用 exe、OCR 增量同步。不要把现有优化当作缺失功能重复实现。
10. 当前 dist 混有旧 exe、日志和用户数据；但 `pack.ps1` 已按白名单打包，不能据此声称 ZIP 已包含用户数据。交接时 exe 为 80,616,047 字节，外置 OCR 目录为 500,636,922 字节，均需在实施时重新测量。
11. `pack.ps1` 顶部“每次构建后必须重新打包”的注释与 AGENTS.md 不一致，应修正文案，保持普通修改不重新打 ZIP。
12. `verify_build.py` 包含与当前模块布局、符号名称绑定的检查。移动实现时要同步调整其定位，不得为了通过重构而删除有价值的校验。

## 三、目标与取舍顺序

1. 首先建立可信、快速、完全无界面的局部验证路径。
2. 消除编辑路径中的全量复制、全量渲染、重复磁盘读取等实际成本。
3. 在正在修改的功能内抽离纯业务逻辑，减少跨功能影响。
4. 精简主界面并保持原有功能可达。
5. 最后评估启动布局和 OCR 裁剪，避免同时修改 UI、数据路径、打包方式三条高风险路径。

不要以“文件数增加”“Mixin 数减少”“创建了四个 State 类”作为成功指标。普通脚本/工作流编辑功能应主要在对应功能目录及测试内完成；确实涉及公共模型或跨功能语义的变更可以修改共享模块。

## 阶段 0：基线与无界面验证通道

- 记录 Python、依赖版本、构建配置、当前源码状态和关键目录体积。
- 先静态盘点测试中的 Tk/Toplevel、应用启动、输入注入、全局钩子和子进程入口，确认哪些测试可安全执行。
- 将能验证纯逻辑、控件调用协议和布局参数的测试改为无 GUI 测试。确实需要真实 Tk 渲染的测试明确标为当前约束下不可运行，在创建窗口之前跳过，并单独报告数量与原因；不得将跳过写成“已经验证”。
- 在此基础上运行 `python -m unittest discover -s tests -t .`，记录通过、失败、跳过及总耗时；记录代表性局部测试耗时。
- 用全新 Python 子进程测量纯模型、存储、应用包的导入耗时和新增模块，不能复用已加载依赖的解释器。
- 性能数据使用固定数据集与机器环境，记录数据规模、预热方式、样本数、p50/p95 和峰值内存；首次测量时保留基线。
- 数据集覆盖 1,000、10,000、20,000 及超过 20,000 条动作，包含跳转引用、嵌套动作、重复引用模块和混合工作流步骤。
- 启动埋点可以写入代码，但不能为收集数据启动 GUI。真实 GUI 冷启动、窗口交互和视觉效果标记为“未测”，由用户正常运行产生数据后再评估。

## 阶段 1：真正切断导入与测试耦合

- 将 MacroFlowApp、MacroPlayer 的组合定义放到各自明确的实现模块；相应包 `__init__.py` 保持轻量，不在包入口加载整套 Mixin。
- 一并检查 `ui/dialogs` 及父包入口；清理兼容重导出和无用导入，不只处理 app/player 两个文件。
- 所有调用方改从真实定义模块导入。同步修复启动入口、测试及产物校验，不保留旧路径别名。
- 从 tests/common.py 移除统一导入面及通配符依赖。仅在确有复用时拆为 tests/helpers/core.py、ui.py、recognition.py、windows.py；helpers/__init__.py 不聚合导入全部帮助模块。
- 纯模型、存储及已抽离的编辑业务测试不能导入 Tk、cv2、numpy、OCR 引擎或 MacroFlowApp；UI 控件适配层测试可以导入 Tk 模块，但不能创建真实窗口。
- 删除 `_PackagePatch`、`patch_app` 等全模块扫描补丁方式。在被测代码实际查找依赖的位置局部 patch；必要时使用少量函数参数或构造参数传入依赖，不建立通用容器。
- 按行为拆测试，优先拆播放器、脚本编辑、工作流和识别；避免只是把一个 common.py 换成多个同样沉重的公共入口。
- 为无界面测试保留简单、明确的 src 导入路径配置，不为解决测试路径新增框架。
- 在 test_module_integrity.py 或同类静态测试中检查依赖方向，解析相对导入及 Import/ImportFrom；用独立子进程检查传递导入闭包。

验收：纯模型/存储导入后没有 tkinter、cv2、numpy、paddle、paddleocr、paddlex；导入轻量 app/player 包入口不加载实现集合；纯业务局部测试可单独运行。每个新增边界测试应证明能捕获一段有意违规的最小示例。

## 阶段 2：编辑性能与最小业务抽离

先处理脚本编辑，再处理工作流；两者分别形成可验证的完整切片。

### 2.1 数据身份与行级更新

- 复用现有 action_id 和工作流 step ID 作为稳定身份；显示行号与数据 ID 分离。不要再依赖 `int(tree.selection()[0])` 推断模型索引。
- 覆盖选择、右键菜单、跳转、搜索、执行高亮、拖动/移动、复制、撤销/重做等所有 ID 调用方。
- 提供少量行级更新方法，如 update_action_row、insert_action_rows、delete_action_rows、update_workflow_row。编辑只更新受影响行，移动优先复用 Treeview.move。
- 插入、删除、移动可能改变后续行号和引用摘要，允许更新真正受影响的范围；不得为了形式上的“只改一行”留下错误行号或跳转提示。
- 保持选择、多选、滚动位置、焦点、片段标记、脏状态、撤销/重做和执行高亮一致。
- 全量重建仅用于打开/替换数据集，或有明确理由的批量操作；禁止单行动作通过 helper 间接触发全量重建。
- 现有工作流将全局模块与普通步骤保存在同一集合、分两个视图显示，必须保持稳定 ID 与原集合映射，避免修改错行。

### 2.2 非渲染开销

- 基准测量必须覆盖“业务修改＋撤销记录＋摘要计算＋行更新”，不能只测 tree.item 或纯函数。
- 单行编辑、插入、删除和移动优先采用局部差异撤销记录，保留嵌套动作隔离和正确重做；仅整体替换等操作按需保存全量快照。不引入通用命令框架。
- 一次刷新只读取/解析一次所需模块配置，优先传入当次快照；不要先建立需要复杂失效策略的永久全局缓存。
- 避免逐行重复读相同脚本/模块文件；确保配置变更后的下一次刷新能看到最新状态。
- 缓存 Font 对象，并在主题、字号、DPI 改变时正确刷新；自动列宽只在打开文档、首次显示或用户主动请求时运行。
- 普通工作流行变化不应无条件重建全局模块表。
- 若测量确认草稿保存或摘要计算仍占主线程主要时间，再处理这条实际瓶颈，不预先新增异步存储层。

### 2.3 大列表

- 先实现可取消的分段填充，再根据实测决定是否需要分页或虚拟化；不要同时实现几套方案。
- 打开另一文档、重新加载、关闭窗口时取消旧填充任务，避免旧回调污染新文档。
- 超过 20,000 条时，所有动作仍必须可定位、编辑和执行，不能继续静默截断可操作范围。
- 所有 Tk 控件操作仍在主线程；分段加载期间的编辑应有明确的一致性处理。

### 2.4 顺势减耦

- 将动作/步骤新增、删除、移动、复制、启停、引用关系维护、摘要计算和保存前整理移至对应功能的无 Tk 模块。
- UI 只读取输入、调用业务函数和刷新控件；业务模块不得使用 Tk Variable、控件、messagebox 或 root.after。
- 只为实际迁移的功能引入 ScriptEditorState、WorkflowEditorState 等简单状态对象。ExecutionState、SettingsState 仅在相应职责确实需要收拢时创建，不一次性创建空壳。
- 模型、状态对象和 Tk Variable 不得各保存一份会独立变化的权威状态。
- MacroFlowApp 逐步收敛为组合入口和生命周期管理器；不新增业务方法和业务状态。
- 脚本页和工作流页不直接操作彼此控件；必要协作用少量明确函数/方法或回调表达，不使用事件总线。
- 不一次重写全部 Mixin，不移动与当前切片无关的代码。

## 阶段 3：主界面减法

- 默认窗口目标约 1100×700，在约 1024 逻辑像素宽度下主要操作仍可用。尺寸按 96 DPI 设计并随 DPI 缩放，不能把物理像素和逻辑像素混为一谈。
- 同时调整最小窗口尺寸、列最小宽度、工具栏换行和必要滚动策略；不能只把侧栏缩窄。
- 左侧栏目标 240–260 逻辑像素，常驻保留开始录制 F8、执行脚本 F9、紧急停止 F12、当前目标窗口和设置入口；目标窗口仍可更换。
- 明确“执行脚本”和“执行工作流”的入口与快捷键语义，避免页签切换后标签与实际行为不一致。
- 录制、执行、启动与备份设置收进独立设置对话框，复用现有设置模型与保存逻辑。明确哪些设置即时生效，哪些需要应用/取消，避免关闭对话框意外保存。
- 主区域保持脚本、工作流、日志三个页签。工作流开始时间、启动延时、默认跳转行收进可折叠设置；全局模块默认折叠，无模块时简化为“添加全局检测”。
- 常用工具栏收敛为“+ 添加动作/步骤”、上移、下移、删除、更多；保留双击/Enter 编辑、撤销/重做及已有重要快捷键。
- 低频功能迁入更多菜单或右键菜单，并提供键盘可达路径。整理旧入口到新入口的映射，防止功能丢失。
- 文案统一中文；正文至少 10pt。蓝色用于主操作，红色用于危险操作；普通启用状态不使用大面积绿色底色，状态同时有文字或图标。
- 提供无 GUI 的布局参数、按钮命令、菜单完整性和状态联动测试。不声称已经完成视觉或真实窗口布局验收。

## 阶段 4：启动与后台生命周期

- 保留已有 PaddleOCR 惰性初始化；将 OpenCV、NumPy、复杂识别对话框等从普通启动导入链移到对应功能首次使用路径。
- 仅改变真正需要延迟的依赖，不在整个项目随意散布函数级 import。静态产物检查仍要保证首次使用需要的依赖被正确收集。
- 首次识别/OCR 加载提供明确进度和失败信息；避免把启动卡顿原样移到第一次点击上。涉及后台任务时采用已有工作线程和 UI 更新机制。
- 每项轮询按功能状态决定暂停/恢复。主窗口隐藏并不代表软件无工作：托盘回放、F12 停止、检测、录制，以及主窗口隐藏时的光标悬浮窗仍须正常运行。
- 管理 after ID、线程、钩子及退出清理，避免重复注册、悬空回调或停止后继续更新。
- 启动埋点区分 Python 入口、根窗口创建、主窗口构建完成、首个 idle 回调。首个 idle 只是代理指标，不等于经人工确认的可交互。
- Python 入口内的计时不能包含 one-file 解包和 Python 初始化之前的时间；端到端冷启动需要进程外计时。本任务禁止启动 GUI，因此不得填造冷启动数字。

## 阶段 5：发布目录、构建可靠性与体积

### 5.1 数据与产物分离

- 明确区分程序资源根目录和可写用户数据根目录。默认采用一个确定的数据位置，例如 `%LOCALAPPDATA%/MacroFlowStudio`，不新增多种自动回退路径。
- 覆盖脚本、工作流、图片、模块配置、设置、日志、崩溃日志、草稿、备份及相对路径解析；资源和 OCR 模型继续从发布资源路径定位。
- 不自动扫描、搬运或删除旧数据，不为旧格式增加迁移层。提供清楚的人工转移说明，并说明相对路径、外部引用和启动配置需要如何调整。
- 当前 dist 中已有用户数据，不得直接 Remove-Item 清空 dist。切换目录前先确认新数据路径及旧数据保留方案，必要时向用户确认数据处置。
- 发布过程在全新暂存目录组装，只允许程序、依赖、OCR 组件及发布文档；通过校验后再交付。构建缓存可复用，发布暂存目录不可复用脏内容。
- 校验暂存目录及 ZIP 清单，不只检查 exe 存在。旧 exe、logs、backups、用户 images/scripts/workflows 和个人设置不得进入发布内容。

### 5.2 构建与 one-folder

- 保留已有增量构建能力，检查缓存键是否覆盖实际构建输入，包括依赖版本/锁定信息、OCR 闭包清单、相关构建脚本和必要环境信息。
- 构建失败不能把失败输入写成成功状态；成功标记应对应通过必需检查的产物。暂存、同步、清理、复制失败必须可靠地导致流程失败。
- 评估 one-folder 时同时更新 spec、build.ps1、pack.ps1、verify_build.py、资源定位、OCR 路径、启动注册与重新启动逻辑。
- 不仅比较 exe 大小，还比较发布目录总量、ZIP 大小、构建耗时及可取得的启动指标；不能因为 one-folder 的 exe 小就宣称总体积下降。
- one-folder 只有在资源与产物校验完整、收益有依据时采用；缺少真实 GUI 冷启动数据时明确保留该验证项。

### 5.3 OCR 裁剪

- 先列出 OCR 文件/目录体积排行、运行时导入闭包、原生 DLL、元数据、模型及包资源依赖。
- 不凭名称删除依赖，也不只依据静态 Python 导入闭包裁剪动态导入、DLL 或资源。
- 每组删除后同时执行静态检查和无界面离线 OCR 回归。优先复用 tests/check_packaged_ocr.py 的能力，但先检查其路径假设、输出位置和联网行为。
- OCR 回归使用实际发布布局并隔离开发机 .deps/site-packages，防止缺失依赖被本机环境补齐。测试所需图片和输出放临时目录，不写入用户数据目录。
- 不在运行时联网下载 OCR；本地组件或模型缺失时给出明确错误。
- 如果 OCR 仍占绝大部分体积，可交付基础版与 OCR 完整版，两者共用源码和发布流程，仅发布内容不同，不做插件框架。
- 基础版保留录制、回放和识图；加载含 OCR 动作的文件不能破坏或删掉动作，执行前明确提示缺少 OCR 能力，不得静默跳过。

## 四、回归与验收

必须覆盖：

- 编辑后 ID 唯一性、复制时内部引用重映射、删除/移动后的跳转语义与显示行号。
- 连续编辑、撤销、重做、多选、嵌套动作、跨文档切换及超过 20,000 条动作的定位。
- 混合工作流集合的行映射，以及全局模块启用状态、注册配置变更后的刷新。
- 分段加载取消和过期回调；停止/退出后任务清理。
- 录制、回放时间线、窗口绑定、F12 停止、输入释放和焦点保护的原有非 GUI 回归。
- 数据路径分离后的保存、加载、图片引用和备份；暂存产物清单及打包完整性。

性能目标分开报告：

- 可自动验证：10,000 条数据下，普通单行编辑的业务、撤销记录和行更新调度整体 p95 目标低于 50ms；记录端点、FakeTree 使用情况和限制。不能把 FakeTree 测量当作真实 Tk 渲染性能。
- 复杂度检查：单行编辑不得清空/重插所有节点，不得复制整个动作集合，不得扫描测量全部文本；磁盘读取次数不能随同一模块引用行数线性增长。
- 待用户实际运行验证：真实 GUI 单行编辑低于 50ms、页签切换/按钮反馈低于 100ms、打包版端到端冷启动低于 3 秒。这些是目标，不是当前承诺，也不能用导入时间替代。
- 未达到目标时报告实测值、瓶颈和剩余工作；禁止删测试、放宽指标或省略慢路径以制造通过。

## 五、防止重新耦合

- core 和纯业务模块不得导入 UI；纯脚本/工作流业务测试不得导入 MacroFlowApp。
- 低层模块不得从 app/player/dialogs 聚合入口取得内部实现。
- 不新增通配符重导出、动态兼容转发、遍历所有子模块的 patch 或反射调用。
- 状态和业务逻辑的所有权明确，不能把原先大 self 变成另一个万能 context。
- 现有执行层直接调用 UI 高亮的依赖应在涉及该功能时通过一个明确可选回调隔离，不扩展成通用事件机制。
- 架构规则既检查直接导入，也用干净进程检查传递导入；不要仅凭文件已拆分认定减耦完成。

## 六、交付节奏

- 推荐顺序：测试安全边界与基线 → 包入口/测试减耦 → 脚本编辑完整切片 → 工作流编辑完整切片 → UI 减法 → 延迟加载/生命周期 → 数据与发布隔离 → one-folder/OCR 体积评估。
- 开发过程只跑相关非 GUI 测试，不每个小修改都构建。
- 每个阶段收尾属于交付检查点：执行全量测试、`.\build.ps1` 和 `python verify_build.py`；如产物布局变化，同步更新校验程序再运行。记录跳过项和未验证项。
- 同一阶段内多个小改可共用一次交付构建，不能以“批量优化”为由跨越交付点留下旧 exe。
- 普通阶段只更新 exe；重大功能级交付或用户明确要求时才运行 `.\pack.ps1`，且必须先成功执行 `.\build.ps1`。未重打的旧 ZIP 不得称为最新包。
- 每个阶段分别组织可审查的改动；仅提交本任务拥有的改动，不打包提交他人已有修改，不把全部重构混成一次巨大提交。
- 每阶段报告：具体改变、验证命令和结果、基线与实测对比、已跳过/未验证内容、剩余风险。无需逐个步骤请求审批，遇到真实阻塞才说明。
