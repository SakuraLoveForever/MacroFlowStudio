# ZeusTool 路线录制与执行逆向分析

分析日期：2026-10-12。对象：`研究/挂机脚本/ZeusTool.exe`，以及配套的 `plugin64.dll`、`luzhi.exe`。本轮只执行后台静态分析，没有启动目标程序或游戏，没有修改原件，也没有修改 MacroFlow 产品代码。

## 结论

这次实际使用反编译器生成了函数级伪代码，并用反汇编复核关键分支。已经还原主程序的**快捷键采点、路线文件导出**，以及**运行时状态反馈 → 路线索引推进 → 移动命令发布**这一段逻辑。路线文件经脚本解释进入原生路线数组的注册/调用关系尚未完整恢复。

它的内置路线录制确实采用“按键时采当前位置”，而不是靠完整键鼠时间轴还原走路。但已还原的路线点没有保存目标朝向；普通路线的到点判定使用前两轴距离，调用处传入的阈值是 **50 个游戏坐标单位**。这不能直接满足“指定位置必须严格到达，并且转向正确”。

**没有恢复完整原始源码。** 主 EXE 仍有 VMProtect 保护，游戏侧如何把目标坐标变成实际移动和朝向尚未完整还原；Lua 名称到所有原生函数的注册关系也未全部恢复。下面的函数名称是分析时赋予的语义名称，不是恢复出的原始符号。

## 1. 快捷键采点：确实只记录当前位置和点类型

主程序函数 `0x4c5910` 检查回调参数 `code == 0`、消息 `0x100`，再检查键码：

| 键码 | 按键 | 写入标记 | 导出函数中的注释 |
|---|---|---:|---|
| `0x55` | U | 0 | 空注释 |
| `0x49` | I | 6 | 门 |
| `0x4f` | O | 3 | 蹲 |

三个分支都调用 `0x4a3390` 读取位置，再把 **16 字节**写入同一个数组。经指令复核，结构可表示为：

```cpp
// 分析后修正类型的示意，不是原始源码。
struct RecordedPoint {
    float x;       // +0x00
    float y;       // +0x04
    float z;       // +0x08
    int32_t flag;  // +0x0c
};
```

`0x4a3390` 从 `0xbb1c30 / 0xbb1c38 / 0xbb1c40` 读取三个 double，并通过 `cvtpd2ps` 转成 float。它没有在这里进行屏幕 OCR，而是读取主程序内已经更新的坐标缓存。

这个点结构没有时间戳、yaw、pitch、按键持续时间或鼠标轨迹。此回调也未看到按键去重、坐标有效性检查；不能直接照搬它来保证一次按键只产生一个有效点。以上只描述主程序内置采点功能，不代表配套 `luzhi.exe` 的完整录制方式。

证据：[采点伪代码](evidence/record_hotkey.pseudocode.txt)、[读取坐标伪代码](evidence/read_cached_position.pseudocode.txt)、[关键指令](evidence/main-critical.asm.txt)。

## 2. 导出脚本：第四项是标记，不是朝向

导出函数入口为 `0x4c5d60`。核心循环位于 `0x4c60d1–0x4c6152`，每次移动数组指针 `0x10` 字节，读取三项 float 和 `+0x0c` 的整数，使用以下格式串：

```text
mi_addPoint(%.2f, %.2f, %.2f, %d )%s\r\n
```

格式串 VA 为 `0xa3fe18`。汇编中的整数比较与字符串内容共同确认：

| 标记 | 自动注释 | 置信范围 |
|---:|---|---|
| 1 | 跳 | 导出函数确认；当前采点回调未发现产生标记 1 的按键 |
| 3 | 蹲 | 采点回调和导出函数共同确认 |
| 6 | 门 | 采点回调和导出函数共同确认 |

因此不能把 `mi_addPoint(x, y, z, 6)` 解读为目标方向 6。工业示例里标记 5 后面的“终点”是脚本注释，本轮尚未恢复标记 5 的全部特殊语义。

导出还把坐标格式化到两位小数，所以文件本身也不是无限精度的位置记录。

## 3. 运行时：路线数组与状态反馈分离

`0x4a2aa0` 接受三项 float 和一项整数，把坐标转成 double，向运行时数组追加 **32 字节**：

```cpp
struct RuntimePoint {
    double x;       // +0x00
    double y;       // +0x08
    double z;       // +0x10
    int32_t flag;   // +0x18
    // +0x1c：未解释的尾部填充，不据此推断隐藏功能。
};
```

对应全局对象：

- `0xbb1bb8 / 0xbb1bbc / 0xbb1bc0`：数组起点、末尾、容量边界。
- `0xbb1bc4`：当前路线索引。
- `0xbb1bc8`：路线活动标志；不能仅把这个标志当作已到终点。
- `0xbb1c28` 起的 `0x68` 字节：主循环读取并缓存的状态块，坐标位于其中 `+0x08 / +0x10 / +0x18`。

`0x4a1550` 的主循环从映射缓冲区读取状态块，再调用路线推进函数 `0x4a5f80`；推进后写回路线索引。`0x4a4ac0` 把一个 `0x78` 字节命令块发布到映射缓冲区 `+0x110`，并设置 `+0x100` 的标志及 `+0x104` 的长度。

这段链路支持“坐标反馈驱动路线执行”的判断，不支持“把录制时间到了的 W/A/S/D 直接照着播”的解释。命令块各字段与游戏侧具体方法的完整映射仍未还原。

证据：[运行时加点](evidence/append_runtime_point.pseudocode.txt)、[路线主循环](evidence/runtime_loop.pseudocode.txt)、[命令发布](evidence/publish_move_command.pseudocode.txt)。

## 4. 启动与恢复：允许从附近路段继续

`0x4a2b50` 在相应参数开启、状态有效且点数至少为 2 时，枚举相邻路线段，计算当前位置在每条线段前两轴平面上的投影：

```text
t = clamp(dot(P - A, B - A) / |B - A|², 0, 1)
Q = A + t * (B - A)
```

它结合平面距离和第三轴偏差选择候选段，并把目标索引设为该段下一点。常量包括：平面候选范围 3000、优先第三轴偏差范围 80；这些是**选择恢复路段**时的条件，不能误认为最终到点容差。

这类设计适合从中断位置继续。但你的“必须经过的几个点”不能参与自动跨点恢复，否则恢复到后面的路段可能绕过必达点。建议必达点单独形成不可跨越的执行关口。

证据：[启动路线伪代码](evidence/start_runtime_path.pseudocode.txt)。

## 5. 到点推进：已确认是容差到达，不是位置与朝向联合验收

主循环 `0x4a1a1d–0x4a1a47` 从 `0xb41680` 取出两个 double 常量 `50.0`、`1.5`，传入 `0x4a5f80`。

推进函数计算当前点与位置缓存**前两轴**的欧氏距离。`0x4a639b` 和 `0x4a64b4` 的比较确认，普通分支使用 `distance < 50.0`；满足后可以增加索引。该比较处没有同时验证第三轴和目标朝向。

还存在按标记进入不同阶段的行为：标记 2 在范围内累计 `0.05`，与传入的 `1.5` 比较；标记 1/3 转入动作阶段；前一个点标记 6 时有周期性命令字段变化。虽然跳/蹲/门的注释已经确认，但完整命令字段尚未命名，因此不把这些字段擅自解释成某个具体虚拟键。

路线之外，`0x4a5080` 还包含线段投影计算；在偏离路线时，推进函数会使用其结果构造移动命令。这进一步说明“跟随路线”与“严格到达指定点”应分开设计。

**50 的单位是游戏坐标单位，未校准成米或屏幕像素。** 此处只确认已还原分支的行为，不能据此宣称全部模式均忽略高度、全部模式采用同一阈值，或游戏侧没有任何朝向控制。

证据：[路线推进伪代码](evidence/advance_runtime_path.pseudocode.txt)、[关键指令](evidence/main-critical.asm.txt)、[常量与样本清单](evidence/manifest.json)。

## 6. 卡住检测：有独立状态机

主循环还调用 `0x4a71d0`。从数据访问、距离比较和状态转换看，它是进度与卡住监测函数，而不是普通采点函数。

已还原的逻辑包括：

1. 索引变化或特定动作状态下重置进度参考。
2. 比较当前目标距离是否比参考距离减少超过一个参数。
3. 超过等待参数仍未达到上述进度，进入恢复阶段。
4. 恢复阶段有 `0.2 / 0.1 / 0.5` 的时间比较，重试达到次数限制后置待处理状态；另有等待参数控制其后状态变化。

`0x4a3170` 能设置这组参数；旧快照里的值为次数 2、等待 3.0、进度量 50.0、后续等待 10.0。它们是可变参数，不能视为所有用户配置。未还原的辅助调用不擅自命名为跳跃、后退或其他具体恢复动作。

对 MacroFlow 的启发：进度判断应分状态。在“转向中、等待动作完成、停点验收”期间，不能要求位置持续靠近目标；在移动阶段，再判断位置数据是否新鲜、实际距离是否改善、输入是否仍被按住。

证据：[卡住检测伪代码](evidence/stuck_monitor.pseudocode.txt)。

## 7. 键鼠输入：不能把它等同于普通录制回放

本轮重新反编译配套 plugin64.dll 的相关函数：

| VA | 已确认行为 |
|---|---|
| `0x18001fcc0` | 查询内部按键表，脚本按下时返回按下状态，否则转发原始 GetAsyncKeyState |
| `0x18001fe00` | 先读取真实键盘状态，再对脚本按下的键叠加 `0x80` |
| `0x180024790` | 加锁读取每键一个字节的内部状态表 |

因此其输入至少存在“持续按住状态”这一层，真实输入也可能与脚本输入叠加。这里没有证明键鼠事件与路线点之间存在严格同步协议，也没有证明它完全排除用户操作干扰。

`luzhi.exe` 的外层 UPX 已成功解压，导入里有键盘状态、Hook 和计时 API。不过这些也可能属于界面框架；本轮没有恢复其完整业务回调，所以不能仅凭导入表判断录制精度、事件排序或转向录制算法。

证据：[按键查询伪代码](evidence/async_key_state.pseudocode.txt)、[键盘状态伪代码](evidence/keyboard_state.pseudocode.txt)。

## 对你的跑图方案的建议

建议借鉴它的“手动采点 + 位置反馈 + 分阶段执行”，同时增加你所需的严格验收：

```text
前往必达点 → 降速接近 → 松开移动键 → 验收位置
           → 调整 yaw / pitch → 联合验收位置与朝向
           → 执行该点动作块 → 进入下一个必达点
```

- 每个必达点记录三维坐标、yaw、pitch、位置/角度容差及本地动作块；容差按游戏坐标和状态读取精度实测，不直接复制 50。
- 移动阶段由导航器控制移动键和转向；动作块开始前确认移动键已释放。需要同时按下的组合键作为同一组执行，按下/松开明确配对。
- 开门、跳跃、交互等关键动作绑定到位置条件或必达点验收结果。普通非关键动作才使用段内相对时间，避免靠全程时间轴猜测角色位置。
- 必达点必须连续多次取得新鲜状态并通过位置、角度和停稳条件才算成功；转向量取整为零不能算作朝向已经正确。
- 卡住时保留当前必达点，恢复失败则停止并说明失败阶段；自动恢复路段不能越过尚未完成的必达点。

这些是针对当前需求提出的设计建议，不是声称 ZeusTool 已经实现了上述保证。本轮没有修改录制或导航功能。

## 补充：攻击时的鼠标、键盘和路线协调

用户追问后继续反编译了 `0x4a5180 / 0x4a53e0 / 0x4a5450 / 0x4a5550`，分别对应键状态命令、鼠标状态命令、队列单步执行和战斗队列调度。以下新增结论同样只针对已恢复的分支。

### 输入队列保存什么

`0x4a3410 / 0x4a3440` 向普通队列追加记录，`0x4a34a0 / 0x4a34d0` 向另一套队列追加同类记录。每项占 12 字节：

```cpp
struct InputStep {
    int32_t key;         // +0：键盘键码，鼠标项为 0
    int32_t duration;    // +4：保持时长，按名义毫秒步长比较
    int32_t mouse;       // +8：-1 表示键盘项；非负值表示鼠标按钮编号
};
```

队列不是鼠标光标位置序列，也不是把整次录制的绝对时间轴重新播放。执行状态另存：是否运行、当前项索引、是否已经按下、当前项累计时长和冷却参考时间。

### 一项动作如何执行

`0x4a5450` 的指令确认了以下顺序：

1. 尚未按下时，向键盘或鼠标命令函数传入状态 **1**，并清零累计时长。
2. 后续轮次每次把累计值增加 `0x32`（50）；未达到该项时长就继续保持状态 1。
3. 达到时长后传入状态 **0**，再增加项索引；全部完成则清除队列活动标志。

例如“按 1 保持 100，再按 2 保持 100，再按鼠标按钮保持 600”可以表达为三个顺序步骤。数值是说明性示例，不是样本里的固定技能配置。此队列分支会先释放当前项再推进，**没有证明它直接支持多键同时按下的组合动作**。按名义 50 的步长累计也不能保证真实墙钟时间精确到 1ms；调度延迟可能造成实际保持时间变长。

### 输入怎样交给游戏

`0x4a5180` 处理键码和按下/松开状态；存在输入回调时还做键码转换与重复状态抑制。`0x4a53e0` 处理鼠标按钮状态。未配置回调时，两者把键码/键状态、鼠标按钮/鼠标状态等写入映射缓冲区 `+0x300…+0x310`。直接键盘按下/松开的包装函数 `0x4a36a0 / 0x4a36c0` 也分别传入 1/0。

结合前述 plugin64.dll 的状态查询 Hook，可以确认这里有持续按住状态和显式松开状态。尚未完整追出全部接收端，所以不把所有模式都称为 SendInput，也不承诺全部输入分支具有相同的后台行为。

### 普通敌人、Boss 与跑图如何协调

`0x4a5550` 检查状态块中的敌人数与距离，Boss 状态会选择另一套队列；两套队列有各自冷却参数。部分中断分支会释放当前已经按下的队列输入并清除执行状态，但本轮没有证明所有异常退出路径都释放全部键。

已还原的普通路线函数 `0x4a5f80` 先调用战斗处理。如果战斗处理返回非零，就立即退出该次路线推进，**保留当前路线索引**。因此协调点是“战斗状态占用本轮执行”，不是让跑图和攻击各自按独立全程时间轴推进。暂停路线索引不等于已经证明角色在所有模式中都会原地站定；战斗命令还有配置分支，游戏侧完整语义未恢复。

自动开火另有 `mi_startFire / mi_stopFire / mi_setAutoFire` 等脚本接口。它与上述技能队列应分别看待；游戏侧自动瞄准、持续射击和目标选择的完整实现仍未恢复，不能把接口名称当作该部分算法的证据。

对 MacroFlow 的建议是：**必达点验收通过后进入攻击动作块；动作块自己维护按下、保持、松开的状态；完成并释放所持输入后才恢复导航。** 如果需要边走边攻击，应明确允许哪些输入同时使用，并由同一调度器处理，避免导航和攻击同时争用转向或移动键。
