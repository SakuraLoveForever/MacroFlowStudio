# 仓库批量开启：协议路径核查

日期：2026-10-23。需求是以插件形式通过游戏业务协议开启仓库物品，不采用模拟点击。

## 目前结论

扫荡工具的已有研究证明了通过游戏现有连接发送 AMF 请求的实现思路，但它的 `raidRpgBattleField`、`exchangeStorageItem` 不能直接当作通用开箱接口。

本轮从本机已有的大厅 ABC 静态分析文件确认了物品使用路径。**尚未实现或交付运行插件，也未验证当前服务器接受这些请求。** 不把仅有接口名的代码做成可执行的批量消耗入口。

## 静态证据

来源目录：`E:/SSJJ-4399/analysis/adventure-rewards/`。读取已有 `abc-metadata.json`，使用该目录已有的 `inspect_ops.py` 解码选定方法。对应大厅文件为 `Lobby_6c54301edd140e1557d4793e0aceaa6c.swf`，不是本轮从运行进程导出的镜像。

完整的输入文件摘要、方法签名、原始方法体字节与 AVM2 指令保存在 [warehouse-methods-2026-10-23.json](evidence/warehouse-methods-2026-10-23.json)。方法编号只适用于该份 ABC 元数据，不能作为其他版本的固定入口地址。

`UseItemPanel.onUseBtnMouseClick`（29416）读取界面中的数量值，并按物品 VO 类型分支。`PackVO` 分支读取 `_commonItemVO.id`、转为字符串，连同数量调用 `useStoragePack`（字节码偏移 284–316）；`RunesPackVO` 分支调用 `useStorageRunePack`。因此这里使用的是物品对象的实例身份，不能用截图上的名称或静态模板编号代替；它与登录库存字段的对应关系仍需要确认。

`ChosenBoxPanel.onConfirm`（45385）先检查选项数和开启数量，将所选奖励配置的 `index - 1` 收集成数组，再调用 `useChosenBoxMulti`。因此自选箱存在必须明确的奖励选择，不能自动按普通礼包处理。

`onUseStoragePack` 的签名是 `(int, Array)`，本轮观察到它把 Array 转交给 `SHOW_PACK_ITEMS` 通知。不能仅凭参数类型断言首个整数的状态码语义，或把本地奖励展示当成库存扣减已确认。

## 与扫荡工具的关系

沿用 [2026-10-22 静态报告](2026-10-22-reverse-analysis.md) 中已核对的样本身份与收发链路：内嵌 x86 DLL 拦截 `send/recv`，保存游戏连接，序列化 AMF 后经原发送函数发送。该工具已有登录 `storageMap` 解析线索。

本轮打开相同 SHA-256 的 `sz.dat` 做定向字符串查询，深度分析在 300 秒调用时限到达后未返回结果，随后关闭 REA 会话。没有把这次超时查询记作成功证据，也没有以字符串存在证明完整调用链。

当前本机进程清点发现 `MicroClient64/MicroClient.exe` 与战斗端正在运行；只读取了进程名和可执行文件路径。没有检查目标进程架构、加载模块或实际大厅版本，不能认定旧 x86 DLL 可以直接复用。样本没有提供可直接集成的源码、稳定插件 API 或已核实的再分发授权，本轮不加载或分发它。

## 实现前仍需补齐

1. 当前大厅通过正常操作打开一个普通礼包时的请求、回包以及后续库存更新。确认实例 ID、数量、消息封装、状态码及关联规则；采样本身不发送额外业务请求。
2. 当前账号完整库存的读取来源和生命周期。旧工具的登录 `storageMap` 线索不等于可以在任意时刻独立查询库存；不能用过期记录或其他账号的 ID 批量发送。
3. 连接接入方式与目标架构。直接请求必须复用经过认证的会话，不能另开未经认证的 socket 并假定已登录。
4. 按类型确定开启资格、数量上限、是否需要钥匙/额外货币，以及自选奖励策略。自选箱和兑换材料不能被普通礼包请求覆盖。

形成插件时应先完成库存预览，再按已验证类型逐项发送、逐项等待确认并更新库存；超时结果不明时先对账，避免重复消耗。沿用 F12 停止入口，在途请求的真实结果以服务器回包为准。
