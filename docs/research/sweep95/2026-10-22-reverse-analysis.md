# 扫荡＋95 分解工具 0.16 静态逆向

日期：2026-10-22。使用 REA 6.4.0、Ghidra 12.1.4 和 Capstone 5.0.7。未启动目标软件、操作界面、访问游戏进程或发送请求。

## 结论

它在客户端通信层直接构造并发送业务请求，所以可以省掉游戏里的逐项点击。扫荡路径中恢复到的请求名是 **`raidRpgBattleField`**；合成、进化、分解路径使用 **`exchangeStorageItem`**。代码会把请求对象转换为 AMF，再通过已有 socket 的原始发送函数发送。

合成／分解还实现了回包匹配、物品数据库 ID 接续、失败处理、超时与重试。静态证据支持“跳过界面交互”，没有证明它能跳过服务器资源、资格、次数或其他校验，也没有测量实际执行耗时。

## 扫荡为什么能省掉点击

静态解析 DLL 的对话框资源和 MFC 消息表，得到“点击扫荡”按钮 ID 为 `0x3f3`，消息表地址 `0x10225180`，处理函数为 `FUN_1001c680`。

处理函数禁用相关控件并创建后台线程。线程入口 `FUN_100445e0` 调用 `FUN_1001d860`。该函数检查所选关卡，调用 `FUN_10036310` 组织关卡编号，再进入 `FUN_10031f70` 发送请求。

在 `FUN_10031f70` 使用的数据处，静态还原出合法 JSON 模板：

```text
@type: common.net.APC
functionName: raidRpgBattleField
isTrace: true
parameters: [关卡编号, 对应参数, 标志]
```

原始模板含固定示例值；实际发送前代码会设置参数。模板位于 DLL VA `0x10224e81`，长度 144 字节，使用 `decoded[i] = encoded[i] XOR ((0x86+i) & 0xff)` 可还原明文并通过 JSON 解析。完整默认值、原始位置、编码字节摘要和还原公式保留在 [raid-template.json](evidence/raid-template.json)。这是文件字节的静态还原，**不是抓到的实际请求**。

`FUN_10031f70` 中还存在按 `64、32、16、8、4、2、1` 七个标志逐项构造并发送请求的循环。`FUN_10036310` 负责按选择项枚举关卡。因而它能批量触发协议操作，省掉在游戏界面内逐项定位、点击和等待界面变化的过程。每个标志的服务器业务含义尚未逐一确认。

同一扫荡工作函数还包含可从立即数字节还原出的 `resetRpgArenaData` 请求；这说明部分选项带额外请求步骤，不能把所有关卡分支概括为完全相同的一次发送。

## 95 合成、进化与分解

`FUN_10003e80` 构造 `exchangeStorageItem` 请求，完成对象转换和序列化后经原发送函数发送。DLL 中同时存在 `common.net.APC` 与该方法名的明文模板。

`FUN_100096b0` 遍历操作链：

1. 保存本步预期的操作编号并清空旧回包状态。
2. 发送 `exchangeStorageItem` 请求。
3. 等待回包；操作编号不匹配时记录并继续等待。
4. 成功时取回物品 `dbId`，作为下一步使用的物品身份。
5. 拒绝、超时、重试次数用尽或用户停止时，进入相应失败／停止分支。

`FUN_10011990` 的解析代码和日志包含 `onExchangeStorageItem`、`actCode`、失败码、`parameters[3]` 中的 `dbId` 检查。`FUN_10009b20` 则组织整批任务和统计。

资源及日志可确认的任务选项包括 95 改 II／改 III 的合成进化分解链、仓库 95-1 进化后分解、仅分解改 II／改 III，以及荒野屠夫、黄金战盾、金属风暴相关链。存在“忽略分解失败”和“野蛮模式”选项；本轮没有把所有选项参数和每个交换编号的服务器语义完整还原。

因此，“直接完成”的关键在于协议调用与状态推进，而不是单纯把鼠标点击间隔缩短。成功与否仍会反映在回包路径中。

反编译产物是伪代码，包含混淆算术和类型恢复误差，特别是 ECX／EDX／XMM 参数。它不是原始源码，不能直接复制作为可运行实现。当前服务器协议兼容性、完整加载链、全部关卡效果和所有业务校验均未进行动态验证。
