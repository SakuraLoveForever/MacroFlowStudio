核验日期：2026-10-13。按用户请求使用 REA 分析提供的安装包，并对照手册、包内路线和当前 Macro 源码。没有运行安装器、目标程序、目标 PYD 或游戏，没有进行界面测试；本文不声称观察到了实际运行行为。

## 结论与证据等级

1. **不能把 7.0.9 概括成“只截取左上角小地图来纠错”。** 包内同时存在视觉定位相关模块、二维图像路线、世界 XYZ 路线、内存读取相关模块，以及 Reader 的 `read_world_state`、`read_pose`、`to_pixel`、`to_world` 接口。它具备混合导航架构的证据；具体地图、设置和会话中选择哪条链路，尚未完整还原运行分支。
2. **读取坐标后投影到二维导航平面，与截图识别小地图是不同步骤。** REA 已反编译 Reader 的投影及正反转换函数。即使控制器使用二维点，坐标来源也可以是世界坐标；打开小地图、路线点是二维，都不能单独证明视觉定位。
3. **当前 Macro 可以确认直接读取游戏进程内存。** `src/macroflow/execution/ssjj_state.py` 的 `SSJJReader` 调用 `OpenProcess`、`ReadProcessMemory`，提供 XYZ、yaw、pitch、死亡、落地及客户端时间等状态。本文未取得明确标识为用户所说“魂飞”的对应版本来比较，故不能确认魂飞的实现与 Macro 完全相同。
4. **包内有大量预置路线，尚不能证明能从任意地图自动生成任意起终点的通路。** 路线层含提取、BFS、简化和加密度函数；这与沿图像路线搜点相符，但不能扩大成完整场景 NavMesh 或全图 A* 已恢复。场景几何加载模块存在，几何内容未成功解码。
5. **目标附带录制工具的新版格式仍以人工控制点为主。** 字符串与落盘数据表明它区分预览轨迹和最终保存的控制点。用户提出的“自动持续保存每次读到的位置状态，无需 F7”是独立的产品要求，不能因为目标录制工具存在就认为已经满足。

## 对 Macro 录制改进的含义

当前录制器并非完整状态录制：`RouteCapture.feed` 只保存时间和 XYZ，F6/F7 标记才保存姿态并形成检查点；开始和结束仍依赖手工标记。`SSJJMonitor` 约每 0.05 秒读取一次，状态对象已有 yaw、pitch、落地、死亡、客户端时间及 details。可以在现有数据链上改进，无需先增加截图定位。

正确的目标是：从有效状态开始连续采样，保存每次实际读到的新鲜状态；静止转头、跳跃阶段和停留时间也有意义，不能只按位移去重。采样频率受读取周期限制，不应声称保存了游戏每一帧。

回放仍需使用实际位置/姿态反馈。仅记录 WASD 和持续时间无法保证坐标重合，帧率、速度、碰撞及起始姿态会使误差累积；WASD 可作意图信息，不能代替位置反馈。现有回放已过滤原始 WASD，由导航根据当前位置控制行走、转向并同步非移动动作。

连续样本不能全部变成必须停下来的检查点。路径追踪应连续推进，定点姿态和特殊动作才形成约束；还需区分移动方向和视角，才能保留侧移/倒退时的姿态。闭环也只能把误差控制在明确容差内，不能保证每个位置逐点完全一致。

本轮只完成研究记录，**没有修改产品录制和回放行为**。具体实现需要在现有输入租约、失焦释放、状态新鲜度和路径进度保护上逐层增加，不能以复制目标的 F7 录制模式替代用户要求。
